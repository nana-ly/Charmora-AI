# ShopGuide RAG 后端技术文档

本文档说明当前后端模块边界、核心链路、日志策略和扩展方式。README 只保留快速运行和验收信息；维护、扩展或联调时优先阅读本文档。

## 1. 后端定位

后端负责把用户的自然语言购物需求转换成可展示的商品推荐结果，并为客户端提供稳定 JSON 和 SSE 接口。

当前已实现：

- FastAPI HTTP 服务。
- 本地 JSON 商品数据加载。
- 规则版需求解析：品类、预算、品牌、关键词。
- 严格结构化候选筛选。
- 关键词检索和 RAG 向量检索。
- 商品卡片响应组装。
- 可选 LLM 推荐理由生成。
- LangGraph 多轮导购 Agent。
- Agent 理解层规范化、确定性兜底、泛品类推荐、跨目标上下文归档和恢复确认。
- 当前购买上下文内的负反馈排除，例如排除第 N 个商品或排除品牌。
- SSE 流式对话接口。
- 控制台日志配置。

## 2. 分层结构

后端按职责分为五层：

1. `api/`：只处理 HTTP 请求、响应和 SSE 事件。
2. `services/`：装配应用服务，例如选择 vector/keyword 检索、为 Agent 注入推荐入口。
3. `agent/`：使用 LangGraph 编排多轮导购状态和动作。
4. `recommendation_core/` 与 `retrieval/`：分别负责推荐 pipeline 和检索实现。
5. `rag/shopguide_rag`：负责商品向量索引构建和 ChromaDB 查询封装。

`main.py` 不再承载业务逻辑，只创建 FastAPI 应用并挂载路由；公共导出仅保留 `app`。
`api/deps.py` 持有应用级 Agent Runner 单例，并把 `RecommendationTool(recommend_func=run_recommendation)` 注入给 `/chat` 和 `/chat/stream`，因此对话接口的推荐工具会复用 `services.recommendation_service` 中的配置化检索选择。

当前后端分层链路为：

```text
api/* -> services/* -> retrieval/* + recommendation_core/* -> schemas/*
```

```text
backend/
  main.py                  FastAPI 应用入口
  api/                     HTTP 路由
  services/                应用服务装配
  core/                    应用配置和控制台日志配置
  schemas/                 接口模型
  recommendation_core/     推荐核心链路
  retrieval/               检索抽象和实现
  llm/                     LLM 客户端和理由服务
  agent/                   Agent 工厂、理解层、上下文管理和 LangGraph 编排
  tests/                   后端测试
```

## 4. 推荐链路

`POST /recommend` 通过 `services.recommendation_service.run_recommendation(query)` 执行推荐。

```text
request.query
  -> services.retriever_factory.select_retriever(config)
  -> recommendation_core.pipeline.recommend_products(...)
  -> extract_filters(query)
  -> choose_candidates(products, filters)
  -> apply_negative_filters(..., negative_filters)
  -> Retriever.search(query, candidates, top_k)
  -> passes_negative_filter(...)
  -> build_response_item(query, retrieval_result)
  -> generate_reason(...)
  -> return {"query", "filters", "items"}
```

`/recommend` 的应用层调用链路为：

```text
api.recommend
  -> services.recommendation_service.run_recommendation
  -> services.retriever_factory.select_retriever
  -> recommendation_core.pipeline.recommend_products
  -> Retriever.search
  -> recommendation_core.negative_filter.passes_negative_filter
  -> recommendation_core.response_builder.build_response_item
```

核心规则：

- `choose_candidates()` 只按品类、预算、品牌等结构化条件筛选。
- 没有候选或检索无命中时，`items` 返回空数组。
- 推荐链路异常向上抛出，便于测试、监控和 API 层暴露真实问题。
- `DEFAULT_TOP_K` 控制默认推荐数量。
- `RETRIEVER_MODE=vector` 使用向量检索；`RETRIEVER_MODE=keyword` 使用关键词检索。
- 负反馈只通过 `NegativeFilters` 进入推荐链路，不拼进正向 query。当前硬过滤生效字段是 `excluded_product_ids` 和 `excluded_brands`；`excluded_keywords`、`excluded_price_ranges` 已在 schema 中预留。

## 5. 检索层

检索层通过 `Retriever.search()` 暴露统一接口：

```python
def search(
    query: str,
    candidates: list[dict] | None = None,
    top_k: int = 3,
) -> list[RetrievalResult]:
    ...
```

`RetrievalResult` 包含：

```text
product   原始商品字典
evidence  可展示给用户的中文匹配依据
score     检索或排序分数
```

`services.retriever_factory.select_retriever()` 负责读取配置并选择检索器对象。向量模式下，向量检索创建或查询失败会暴露错误；关键词模式下返回本地 `KeywordRetriever`。

检索实现边界：

- `KeywordRetriever` 使用 `extract_filters(query)["keywords"]` 作为关键词集合，并对标题、子类目、品牌、类目和营销描述做加权命中排序。
- `VectorRetriever` 复用 `rag/shopguide_rag.ProductVectorStore`，默认读取 `rag/.chroma/products` 集合；当调用方传入候选集时，会先扩大向量召回数量，再按候选商品 ID 回收结果，保证结构化筛选不会被向量召回绕过。
- `/rag/search` 是向量召回调试接口，始终创建 `VectorRetriever`，不受 `RETRIEVER_MODE=keyword` 影响。

## 6. LLM 与模板理由

LLM 是增强能力，不是推荐链路的硬依赖。

相关环境变量：

```text
LLM_ENABLED=false
LLM_API_KEY=
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=gpt-4o-mini
LLM_TIMEOUT_SECONDS=8
```

只有 `LLM_ENABLED=true` 且 `LLM_API_KEY` 非空时，后端才会调用 LLM。LLM 不可用、密钥缺失或调用失败时，推荐理由使用 `recommendation_core.reason.template_reason()`。`.env.example` 中给本地运行预留的 `LLM_TIMEOUT_SECONDS` 是 60 秒；代码默认值仍是 8 秒。

`llm.client.create_llm(config)` 提供 `.invoke(messages, max_tokens=...)` 接口，供 LangGraph 意图理解使用。Agent 理解层要求 LLM 返回单个 JSON 对象，并在 Pydantic 校验前执行安全规范化：

- 缺失的理解字段补默认值。
- 非对象 `preference_updates` 或 `negative_updates` 清洗为空对象。
- 非法 `target_item_index`，例如小于 1 的序号，清洗为 `None`。
- 未知字段忽略，只写调试日志。

解析失败、校验失败、LLM 不可用、LLM 调用失败、LLM 在已有上下文中给出空更新，或把明显完整的购买请求误判为澄清时，会进入确定性兜底。兜底只识别明确购买请求、负反馈、上下文内价格反馈和结构化偏好补充，不编造商品。

## 7. 多轮 Agent

`POST /chat` 和 `POST /chat/stream` 通过 LangGraph Runner 编排一轮对话。

```text
session_id + message
  -> InMemoryConversationStore.get_or_create(session_id)
  -> resolve_pending_restore(...)
  -> LLMUserUnderstandingService.understand(...)
  -> filter_item_index_negative_updates_for_current_target(...)
  -> update_memory(...)
  -> apply_negative_feedback(...)
  -> decide_next_action(...)
  -> execute_action(...)
  -> generate_reply(...)
  -> return ChatResponse
```

当前 `AGENT_RUNNER=langgraph` 是默认且唯一支持的模式。Agent 只编排状态和工具调用，不直接实现检索、排序或索引逻辑。

理解层和状态层分工：

- `understanding.py`：LLM JSON 解析、默认字段补齐、保守澄清兜底。
- `category_rules.py`：目标品类、安全购买信号、泛品类信号、恢复确认/拒绝和轻量偏好提取。
- `fallback_understanding.py`：LLM 不可用或不可用输出时的保守购买请求识别。
- `policy.py`：根据理解结果、会话状态和负反馈应用结果选择下一步动作。
- `reply_builder.py`：集中构造推荐、无结果、工具错误、解释、对比和澄清文案。
- `tools/`：Agent 工具包。`recommendation.py` 封装推荐链，`explain.py` 只选择上一轮真实商品用于解释，`compare.py` 只基于上一轮真实商品做对比；`tools/__init__.py` 保留 `from agent.tools import ...` 兼容导入。
- `context_manager.py`：购买上下文归档、清空、恢复请求、确认和拒绝。
- `query_builder.py`：从 `purchase_need` 和结构化偏好构建推荐 query。
- `sqlite_memory.py`：SQLite 版 `ConversationStore`，按 `session_id` 保存完整 `ConversationState` JSON。

跨品类切换时，Agent 会先归档当前购买上下文，再清空活跃推荐状态并写入新需求。归档内容包括购买需求、偏好、排除品牌、最近推荐结果和无结果建议。用户疑似回到旧品类时，后端先追问是否恢复旧需求；只有用户确认后才替换活跃上下文。用户拒绝恢复并给出新约束时，后端清除待恢复状态并按新约束推荐。

支持的意图：

```text
recommend
update_preference
explain
compare
clarify
```

`state.action` 当前取值：

```text
recommend
explain
compare
clarify
reply_only
```

推荐执行结果可能在 `state.result_status` 中体现：

```text
success
no_results
tool_error
```

`no_results` 会返回 `relax_options`，但不会覆盖上一轮成功商品。推荐工具异常会返回可恢复的 `tool_error` 响应，`state.tool_error="recommendation_failed"`，不会伪造商品，也不会把错误当成无结果。

### 泛品类推荐和目标归一化

`/chat` 和 `/chat/stream` 支持“推荐手机”“看看护肤品”“有什么咖啡推荐”这类泛品类请求。理解层会写入：

```text
preferences.target_category
preferences.category
preferences.canonical_target_key
preferences.is_broad_category_request
```

`target_category` 表示用户说的具体购买目标，例如“手机”“护肤品”“咖啡”；`category` 表示数据集类目，例如“数码电子”“美妆护肤”“食品生活”；`canonical_target_key` 用于判断跨目标切换和上下文恢复，例如“手机”归一为 `phone`，“护肤”“护肤品”“化妆品”归一到同一类护肤目标。

泛品类请求会先返回代表性推荐，并提示用户继续补充预算、品牌或使用场景。本轮是否泛品类由 `current_turn_is_broad` 判断；写入状态的 `preferences.is_broad_category_request` 是当前轮语义，后续用户补充预算、品牌、用途等具体约束时会写回 `False`，避免复用旧的泛品类回复文案。

推荐 query 由 `query_builder.build_recommendation_query()` 从 `purchase_need` 和结构化偏好组装。它会清理负向短语，补入预算、目标品类、数据类目、品牌、偏好品牌和关注点；如果用户在已有上下文中说“太贵了”“便宜点”，兜底会写入 `price_direction=lower` 和 `avoid_current_price_band=True`，query 中会补入“价格更低”“性价比优先”“避免上一轮同价位”。

### 负反馈排除链路

负反馈链路分为五层：自然语言解析、`negative_updates`、`NegativeFeedbackApplicationResult`、`ConversationState` 顶层负偏好、推荐链路 `NegativeFilters`。

用户说“不要第 2 个”“不要苹果”时，理解层优先从 LLM 结构化结果读取 `negative_updates`，规则兜底只补确定性短句。Runner 调用 `apply_negative_feedback()`，把应用结果记录为 `NegativeFeedbackApplicationResult`：可区分 `applied`、`removed`、`noop`、`needs_clarification`，并携带目标商品或品牌，供回复和 `/chat.state.negative_feedback` 复用。

生效的负偏好写入 `ConversationState` 顶层字段，例如 `excluded_product_ids`、`excluded_brands`、`excluded_keywords` 和预留的 `excluded_price_ranges`。这些字段跟随当前购买上下文归档和恢复，不作为跨品类全局偏好。`preferences["excluded_brands"]` 只作为历史兼容输入，在 Runner 偏好合并入口通过 `pop()` 迁移到顶层后删除，避免正向偏好和负向排除混在同一个 map 中。

推荐前，Agent 将 `ConversationState` 转成 `NegativeFilters` 传给 `RecommendationTool`，不会把“不要苹果”拼进推荐 query。推荐核心链路有两个 product_id/brand 硬过滤点：检索前先过滤候选商品，避免被排除商品进入召回；构建 `ProductCard` 前再过滤检索结果，防止向量召回或兼容路径漏出已排除商品。

当前支持的确定性负反馈包括：

- `不要第 2 个`、`第 2 款不要`：排除上一轮成功推荐中的对应商品，序号按 1-based 处理。
- `不要第二个`、`排除第三款`：支持中文序号，仍按上一轮成功推荐列表解析。
- `不要这个`、`刚才那个不要`：仅在已有明确解释目标 `target_item_index` 时应用，否则返回澄清。
- `这几个都不要`、`这些都不要`：批量排除当前成功推荐结果内的商品；没有上一轮成功结果时返回澄清。
- `不要苹果`、`不考虑华为`、`排除小米`：排除当前购买上下文中的品牌。
- `苹果也可以`、`取消排除苹果`：恢复考虑已排除品牌。
- 取消排除第 N 个商品仍暂不支持，会返回 `unsupported_negative_type` 的 noop 响应，不会改变推荐结果。

如果用户在切换到新目标的同一轮里说“不要第 2 个”，Runner 会通过 `filter_item_index_negative_updates_for_current_target()` 确认第 N 个仍指向当前活跃结果；目标已变化时不会把旧列表序号错误应用到新目标。

## 8. 控制台日志

### 会话状态存储

默认会话状态仍使用 `InMemoryConversationStore`，适合测试和单进程本地开发。需要演示服务重启后恢复上下文时，可设置：

```text
CONVERSATION_STORE_MODE=sqlite
CONVERSATION_STORE_PATH=data/conversations.sqlite3
```

`SQLiteConversationStore` 表结构为 `conversation_states(session_id, state_json, updated_at)`，保存 `ConversationState.model_dump_json()` 的完整 JSON。读取时通过 `ConversationState.model_validate_json()` 恢复，因此 `messages`、`preferences`、`last_items`、`last_successful_items`、`previous_purchase_contexts` 和负反馈字段会一起往返。显式调用 `create_agent_runner(store=...)` 时，传入的 store 优先于环境配置。

后端日志使用标准库 `logging` 输出到控制台。`main.py` 启动时读取 `LOG_LEVEL` 并调用 `core.logging_config.configure_logging()`。

记录原则：

- 路由层记录请求到达和结果数量。
- 服务层记录检索模式。
- Agent/LLM 层记录意图、数量和模板替代事件。
- 不记录 API Key、完整用户消息、完整用户 query、完整对话历史或外部服务完整响应。

环境变量：

```text
LOG_LEVEL=INFO
```

## 9. 允许的可用性处理

推荐链路不生成预置商品。允许保留的可用性处理只包括：

- LLM 推荐理由使用模板理由。
- Agent 理解层对 LLM 缺字段、JSON 解析失败、校验失败或明显误判进行保守兜底。
- Agent 对泛品类请求返回代表性推荐，并等待用户继续补充约束；这不放宽已有明确约束。
- Agent 对上下文内“太贵了”等短反馈做价格方向更新，而不是请求重新输入品类。
- `/chat` 推荐工具异常返回稳定的 `tool_error` 对话响应，不伪造商品。
- `/chat/stream` 对可恢复 `tool_error` 仍发送正常 `delta -> items -> state -> done` 事件；流开始后的未处理异常才转换成 SSE `error` 事件。

这些处理不会改变商品选择结果。

## 11. 扩展建议

- 接入真实商品服务时优先替换 `recommendation_core/data.py`。
- 增加检索策略时优先扩展 `retrieval/` 和 `services/retriever_factory.py`。
- 扩展 LangGraph 时优先新增 `backend/agent/graph/` 节点或工具。
- 持久化会话时替换 `InMemoryConversationStore`，保持 `get_or_create()` 和 `save()` 行为。
- 扩展可恢复上下文时保持 `PurchaseContext.from_conversation()` 与 `apply_to_conversation()` 字段对称，确保归档/恢复不会丢失负反馈和最近结果状态。
- 扩展负反馈能力时同步更新 `negative_feedback_rules.py`、`negative_feedback.py`、`NegativeFilters` 和推荐链路硬过滤点；不要只清理 query。
- 增加接口字段时使用可选字段扩展，不删除客户端已依赖的商品卡片字段。
