# ShopGuide RAG 设计文档

## 1. 文档目的

本文用于说明 ShopGuide RAG 的系统架构、技术选型、运行依赖、目录结构、配置项和关键问题解决方案。

本文只描述当前代码中已经实现或已经预留的能力；无法从代码确认的内容会明确标注为“待核实”或“未实现”。

## 2. 项目定位

ShopGuide RAG 是一个面向电商导购场景的多轮智能导购 Agent。系统通过 FastAPI 提供后端服务，使用 LangGraph 编排多轮对话状态，将用户自然语言需求转化为可执行的商品推荐、解释、对比和偏好更新动作。

项目的核心目标不是单纯做商品语义搜索，而是构建一个可控的导购链路：

- LLM 负责用户意图理解和可选推荐理由生成。
- 商品筛选、检索、排序、负反馈排除和商品卡片构造由后端确定性逻辑完成。
- 推荐结果来自本地商品数据集或 Chroma 向量索引，不由 LLM 编造。
- Android 原生客户端提供聊天、商品卡片、商品详情、购物车 UI 和语音转文字输入体验。

## 3. 总体架构

```text
Android Client
  |  POST /chat/stream, fallback POST /chat
  v
FastAPI Backend
  |-- api/
  |     |-- /health, /ready
  |     |-- /recommend
  |     |-- /rag/search
  |     |-- /chat, /chat/stream
  |
  |-- Agent Runner (LangGraph)
  |     |-- understand_user
  |     |-- update_memory
  |     |-- decide_next_action
  |     |-- execute_action
  |     |-- generate_reply
  |     `-- finalize_response
  |
  |-- RecommendationService
  |     |-- recommendation_core
  |     |-- retrieval.keyword
  |     |-- retrieval.vector
  |     `-- llm.reason_service
  |
  |-- Data / Index
        |-- ecommerce_agent_dataset/*.json
        `-- rag/.chroma/products
```

系统分为四层：

| 层级 | 主要目录 | 职责 |
| --- | --- | --- |
| 客户端层 | `android/` | Android 原生交互界面，负责聊天输入、SSE 接收、商品卡片展示、详情页、购物车 UI 和语音输入 |
| API 层 | `backend/api/` | FastAPI 路由，暴露健康检查、推荐、RAG 调试检索和多轮对话接口 |
| Agent 与服务层 | `backend/agent/`, `backend/services/` | 多轮状态编排、会话存储、负反馈、动作执行、推荐服务缓存 |
| 推荐与检索层 | `backend/recommendation_core/`, `backend/retrieval/`, `rag/` | 商品数据加载、结构化筛选、关键词检索、向量检索、商品卡片构造 |

## 7. 后端接口设计

当前 FastAPI 服务注册的接口如下：

```http
GET  /
GET  /health
GET  /ready
POST /recommend
POST /rag/search
POST /chat
POST /chat/stream
```

接口职责：

| 接口 | 作用 |
| --- | --- |
| `GET /` | 返回服务名称和运行状态 |
| `GET /health` | 进程存活检查，不初始化推荐依赖 |
| `GET /ready` | 检查推荐依赖是否可用；向量检索不可用时返回 HTTP 503 |
| `POST /recommend` | 单轮商品推荐 |
| `POST /rag/search` | 调试当前检索器的召回结果 |
| `POST /chat` | 多轮导购对话 |
| `POST /chat/stream` | SSE 流式多轮导购对话 |

`/chat/stream` 正常事件顺序为：

```text
start -> delta -> items -> state -> done
```

进入流式处理后如果发生未处理异常，事件顺序为：

```text
start -> error -> done
```

推荐工具的可恢复错误会被转换成稳定 `ChatResponse`，并通过 `state.result_status="tool_error"` 暴露，不会伪造商品。

## 8. Agent 工作流设计

当前 `/chat` 和 `/chat/stream` 使用 `AGENT_RUNNER=langgraph`，这是代码中唯一支持的 Agent Runner。

LangGraph 节点顺序：

```text
START
  -> understand_user
  -> update_memory
  -> decide_next_action
  -> execute_action
  -> generate_reply
  -> finalize_response
  -> END
```

各节点职责：

| 节点 | 职责 |
| --- | --- |
| `understand_user` | 读取会话状态，调用 LLM 理解服务或确定性 fallback，识别推荐、解释、对比、澄清和恢复上下文等意图 |
| `update_memory` | 将理解结果归约到会话状态，处理偏好更新、负反馈、上下文切换和恢复 |
| `decide_next_action` | 根据理解结果和当前状态选择 `recommend`、`explain`、`compare`、`clarify` 或 `reply_only` |
| `execute_action` | 执行推荐、解释或对比工具 |
| `generate_reply` | 根据动作结果生成中文回复 |
| `finalize_response` | 构造 `ChatResponse`，并在成功构造响应后提交会话状态 |

会话状态支持两种存储模式：

| 配置 | 说明 |
| --- | --- |
| `CONVERSATION_STORE_MODE=memory` | 默认模式，进程内保存会话状态，适合本地演示 |
| `CONVERSATION_STORE_MODE=sqlite` | 使用 SQLite 持久化 `ConversationState`，支持服务重启后恢复同一 `session_id` 的多轮状态 |

## 9. 推荐与检索链路

单轮推荐和 Agent 推荐工具共用 `RecommendationService`。服务会在当前 Python 进程内缓存配置、retriever 和 reason service。

推荐链路：

```text
api.recommend / Agent RecommendationTool
  -> RecommendationService.recommend
  -> recommendation_core.pipeline.recommend_products
  -> extract_filters
  -> choose_candidates
  -> apply negative filters before retrieval
  -> Retriever.search
  -> apply final negative filters
  -> build_response_item
```

关键行为：

- `extract_filters()` 从自然语言中解析类目、预算、品牌和关键词。
- `choose_candidates()` 严格按照结构化条件筛选候选商品。
- 负反馈过滤会在检索前和商品卡片构造前各执行一次，避免 retriever 绕过用户明确排除条件。
- `result_count` 表示本轮找到的匹配商品总数，可能大于实际返回的 `items.length`。
- 商品卡片包含 `product_id`、`title`、`brand`、`price`、`price_range`、`reason`、`evidence`、`image_path`、`image_url`、`imageUrl`、`rating`、`sold_count`、`review_count`、`marketing_desc`、`reviews` 和 `faqs`。

检索模式：

| 模式 | 配置 | 说明 |
| --- | --- | --- |
| 关键词检索 | `RETRIEVER_MODE=keyword` | 不依赖外部 Embedding 服务，适合本地快速演示和评委体验 |
| 向量检索 | `RETRIEVER_MODE=vector` | 默认配置，依赖 `rag/.chroma/products` 索引和可用 Embedding API |

向量索引由 `rag/shopguide_rag/cli.py` 构建，默认读取 `../ecommerce_agent_dataset`，默认写入 `rag/.chroma/products`。

## 10. Android 客户端设计

Android 客户端位于 `android/`，核心入口为 `MainActivity`。

当前实现能力：

- 聊天式导购输入和消息列表。
- 优先调用 `POST /chat/stream` 获取 SSE 流式响应。
- 当 SSE 返回 `404` 或 `405` 时回退到 REST `POST /chat`。
- 展示商品卡片、价格、品牌、图片、理由和证据。
- 打开商品详情页 `ProductDetailActivity`。
- 本地购物车 BottomSheet UI。
- 通过百度 ASR 将语音转成文本后发起导购请求。

默认后端地址：

```text
http://10.0.2.2:8000/
```

该地址适用于 Android 模拟器访问宿主机 `127.0.0.1:8000`。真机体验需要把 `RetrofitClient.BASE_URL` 改为电脑局域网 IP，例如 `http://192.168.x.x:8000/`。

当前购物车是客户端本地 UI 能力，不包含真实订单、库存锁定或支付流程。

| `LLM_API_KEY` | 空 | LLM API Key |

- 后端读取 embedding 维度时兼容 `embedding_dimensions`、`dimention` 和 `dimentions`。

- `RETRIEVER_MODE=vector` 不会在失败时静默降级到关键词检索；如果向量依赖不可用，`/ready` 会返回 `not_ready`。

## 12. 关键问题解决方案

### 12.1 降低 LLM 幻觉

系统不让 LLM 直接决定商品结果。LLM 只负责理解用户意图和可选文本生成，商品是否存在、是否满足条件、是否被排除、如何返回卡片，均由后端商品数据和推荐链路决定。

当推荐链路无结果或工具异常时，系统返回空商品列表和稳定状态，不伪造商品。

### 12.2 结构化约束和 RAG 召回结合

导购场景中预算、品类、品牌等硬约束不能只靠语义相似度。项目先做结构化候选过滤，再在候选集合内做关键词或向量召回，避免 RAG 结果绕过硬性条件。

### 12.3 负反馈状态化

用户说“不要第二个”“不要苹果”“这几个都不要”时，系统会把负反馈写入当前购物上下文，而不是简单拼接到 query 中。推荐工具会将 `ConversationState` 转换为 `NegativeFilters`，并在检索前后过滤商品 ID 和品牌。

### 12.4 多轮上下文漂移处理

用户从手机切换到耳机、护肤品等新目标时，旧购物上下文会被归档。用户疑似回到旧目标时，系统先进入待确认状态，再根据确认或拒绝决定是否恢复历史需求。

### 12.5 失败不污染上一轮有效结果

无结果或工具错误不会清空上一轮成功推荐。用户仍可以继续问“为什么第一个适合我”，系统会解释上一轮真实商品，而不是解释空结果或生成虚假内容。

### 12.6 流式体验和 REST 回退

Android 客户端优先使用 `/chat/stream`。如果流式接口不可用，客户端会回退到 `/chat`，保证演示环境中即使 SSE 不可用也能继续体验。

### 12.7 可观测和可评测

后端日志包含 `request_id`、`session_id`、`turn_id` 和节点耗时等字段。推荐 trace 默认关闭，只有服务端开关和请求 debug 同时开启时才返回脱敏 trace。

`eval/` 提供以下离线评测：

- Shopping Agent Eval：覆盖推荐、偏好更新、负反馈、解释、对比和上下文恢复。
- RAG Retrieval Eval：覆盖检索命中、召回、品类/品牌匹配和负反馈排除。
- Context Memory Eval：覆盖多轮偏好保留、跨品类切换和历史需求恢复。

## 14. 当前边界与待核实内容

当前未从代码中确认或当前不是已完成能力的内容：

- 图片上传后的多模态商品理解：当前 Android 有相机和图片读取权限声明，但后端没有已确认的图片理解接口。
- 真实下单、库存、支付和订单履约：当前购物车为本地 UI，不是交易系统。
- 用户认证、权限、限流和生产级网关：当前 API 未实现认证鉴权。
- 生产级分布式会话存储：SQLite 适合本地或轻量演示，不建议直接作为跨机器生产会话存储。
- 真机局域网访问地址需要根据评委现场网络环境确认。
